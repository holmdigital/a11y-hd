### Category B — vitest-axe `toHaveNoViolations` matcher type augmentation
Site: `packages/components/src/_test/axe.ts:56`:
```ts
expect(results).toHaveNoViolations();
```
`toHaveNoViolations` is provided at runtime by `@chialab/vitest-axe`'s default export (see STATE.md Plan 22-01 deviation). It is NOT declared on Vitest's `Assertion` type. Fix: add a module augmentation to `packages/components/src/_test/setup.ts` (so the augmentation is loaded with the test setup):

```ts
declare module 'vitest' {
    interface Assertion<T = unknown> {
        toHaveNoViolations(): T;
    }
    interface AsymmetricMatchersContaining {
        toHaveNoViolations(): unknown;
    }
}
```

Place this block at the top-level (after the imports) in `setup.ts`. It will be picked up by all files because `setup.ts` is included via `vitest.config.ts` `setupFiles`. tsc reads it because `setup.ts` is under `src/` and the tsconfig includes `src/**/*`.

Sanity check before writing: confirm `@chialab/vitest-axe` types do NOT already provide this augmentation. The Plan 22-02 deviation note in STATE.md says the package "ships ONLY the toHaveNoViolations matcher (default export of main entry)" and that `./matchers` "ships types only" — those types may exist but evidently are not being merged into `vitest`'s Assertion interface (otherwise the error wouldn't occur). Executor: `grep -r "toHaveNoViolations" node_modules/@chialab/vitest-axe/` — if a `declare module` block is found there, investigate why it isn't picked up before writing our own; the answer is likely that it augments `chai` not `vitest`, and a re-export `declare module 'vitest'` is what we need.

### Category C — Read-only `ref.current` assignment
Sites:
- `src/RadioGroup/RadioGroup.test.tsx:65`:
  ```ts
  ref={(node) => {
      ref.current = node;  // ERROR: TS2540 Cannot assign to 'current' because it is a read-only property
      captured = node;
  }}
  ```
- `src/SkipLink/SkipLink.test.tsx:49` — identical pattern

Cause: `useRef<HTMLDivElement>(null)` returns `RefObject<T>` whose `current` is `T | null` and READ-ONLY. The intent of these tests is "capture the ref in the parent scope" — `captured` already does that and `ref.current = node` is dead-code that exists only to make the closure feel symmetric.

Fix (minimal, semantics-preserving): just remove the `ref.current = node;` line in both test files. `captured = node;` remains and is what the assertion (`expect(captured).toBe(group)`) reads. The `useRef` itself can stay (or be removed too — but keeping it is safer in case the test author intended the ref for additional assertions that haven't been written; minimal-diff principle).

Alternative if executor finds a downstream read of `ref.current` in the same test: cast `(ref as React.MutableRefObject<HTMLDivElement | null>).current = node;` — but the planner's read of the file showed `captured` is the only consumer, so the simple removal is correct.

### Category D — Unused `@ts-expect-error` directive
Site: `src/_test/helpers/expectKeyboardSequence.test.ts:28`:
```ts
it('throws on step with empty key (failure-mode)', async () => {
    // @ts-expect-error — testing runtime guard
    await expect(expectKeyboardSequence([{ key: '' }])).rejects.toThrow(/empty\/invalid key/);
});
```
Cause: tsc evidently does NOT flag `{ key: '' }` as a type error against the function's signature (the signature accepts strings; `''` is a valid string). The `@ts-expect-error` therefore reports "Unused directive".

Fix: remove the `// @ts-expect-error — testing runtime guard` line entirely. The runtime test still works (the function throws at runtime on empty key per its `non-empty` guard).

### Category E — `LiveRegionLocale` empty-string narrowing
Sites: `src/_i18n/live-region-strings.ts:141` and `:164`:
```ts
const canonical: LiveRegionLocale =
    (locale && LOCALE_ALIASES[locale]) ?? 'en';
```
Cause: `LOCALE_ALIASES[locale]` returns `LiveRegionLocale | undefined`. With `locale && LOCALE_ALIASES[locale]`, when `locale` is an empty string `''` (falsy), the `&&` short-circuits to `''` which is NOT a `LiveRegionLocale`. The `?? 'en'` only catches `null | undefined`, not `''`. TS correctly flags the assignment.

Fix (minimal): change `locale &&` to an explicit truthiness check that excludes empty strings before indexing, AND use `||` instead of `??` so empty-string results also fall through to `'en'`:
```ts
const canonical: LiveRegionLocale =
    (locale ? LOCALE_ALIASES[locale] : undefined) ?? 'en';
```
This narrows correctly: ternary returns `LiveRegionLocale | undefined`; `?? 'en'` resolves to `LiveRegionLocale`. Apply the identical change at both line 141 and line 164.

Behavior preserved: empty-string locale → falls back to 'en' (same as today by coincidence of `LOCALE_ALIASES['']` being undefined → `?? 'en'`). The semantics are byte-equivalent at runtime; only the type-narrowing improves.
